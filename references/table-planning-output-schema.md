# 多维表清单中间输出规范（3.0 MVP）

## 目标

在系统建设澄清完成后，智能体只能输出一个中间结构，用于后续脚本拼装批量构建请求。

智能体 **不负责** 输出最终 API 请求体。

## 唯一允许的输出结构

```json
[
  {
    "table_name": "CRM客户管理",
    "user_requirement": "我需要一个 CRM 客户管理应用，用于管理客户、联系人、商机和跟进记录。主要使用者是销售团队和销售主管。当前痛点是客户信息分散、销售跟进不透明、商机推进过程缺少统一追踪。"
  }
]
```

## 字段定义

### `table_name`

- 类型：字符串
- 含义：拟建设的多维表或应用名称
- 要求：
  - 简洁清晰
  - 使用业务语言命名
  - 不要写成技术实现名

### `user_requirement`

- 类型：字符串
- 含义：提供给下游构建接口的自然语言业务需求描述
- 要求：
  - 必须融合报告阶段和澄清阶段得到的上下文
  - 至少包含系统目标、主要角色、关键流程、核心痛点中的大部分信息
  - 站在业务方视角描述
  - 描述应足够丰富，让下游 API 能独立推导结构

## 生成原则

- 一张表对应一个清晰的业务对象或业务子系统
- 先生成业务语言层面的表清单，不生成字段级结构
- 输出数量以“覆盖关键业务闭环”为准，不追求越多越好
- 每张表都要能说明它为什么存在

## 正例

### 正例 1

```json
[
  {
    "table_name": "招聘管理",
    "user_requirement": "我需要一个招聘管理应用，用于统一管理职位需求、候选人、面试安排、评估反馈和 offer 审批。主要使用者是 HR、部门面试官和用人经理。当前痛点是流程分散在 Excel 和聊天记录里，导致招聘进度难追踪。"
  }
]
```

### 正例 2

```json
[
  {
    "table_name": "项目执行管理",
    "user_requirement": "我需要一个项目执行管理应用，用于跟踪项目立项、任务分解、里程碑推进、风险问题和周报输出。主要使用者是项目经理、项目成员和部门负责人。当前痛点是进度同步依赖人工汇总，风险暴露滞后。"
  }
]
```

## 反例

### 反例 1：错误输出最终 API 请求体

```json
{
  "client_batch_id": "batch-001",
  "items": [
    {
      "client_item_id": "req-001",
      "user_requirement": "..."
    }
  ]
}
```

问题：这是脚本层职责，不是智能体职责。

### 反例 2：错误输出字段级结构

```json
[
  {
    "table_name": "CRM客户管理",
    "fields": ["客户名称", "联系人", "电话", "来源渠道"]
  }
]
```

问题：字段级结构应由下游构建链路推导，不在 MVP 表清单阶段完成。

### 反例 3：需求描述过于空泛

```json
[
  {
    "table_name": "客户管理",
    "user_requirement": "做一个客户管理系统。"
  }
]
```

问题：缺少角色、流程、痛点和目标，无法支撑下游推导。

## 用户确认前的展示建议

向用户展示时，建议同时呈现：

- 表名
- 一句话说明这张表解决什么问题
- 这张表主要服务谁

用户确认前，允许：

- 删除表
- 增加表
- 调整单张表需求描述

只有用户明确确认后，才能进入脚本拼装和 API 调用阶段。
