# 3.0 MVP 范围与兜底说明

## MVP 明确包含

- 企业 AI 场景地图报告生成
- 报告后进入系统构建规划的显式分支
- 3-4 轮系统澄清，信息足够可提前停止
- 中间表清单生成与用户确认
- 通过 `npx basebuilder-cli` 调用批量构建 API
- SSE 进度展示
- 通过 `request_id` 进行流中断后的状态补查

## MVP 明确不做

- 失败项自动重试
- 仅重试失败项的专用逻辑
- Skill 侧 SQLite 或本地任务数据库
- 历史任务中心
- 独立前端页面

## 对用户的反馈原则

- 先把一次完整闭环跑通
- 不夸大当前能力
- 对未实现能力明确说明

## 流式执行失败时怎么说

### 情况 1：提交前或刚提交就失败，尚未拿到 `request_id`

建议表达：

> 构建请求还没有成功进入执行阶段，这次没有拿到可追踪的请求 ID。建议我根据当前确认好的表清单重新发起一次构建。

### 情况 2：已经拿到 `request_id`，但 SSE 中断

建议表达：

> 构建请求已经进入执行阶段，我拿到了 `request_id`，现在会改用状态查询接口补查当前进度。

### 情况 3：状态接口也不可用

建议表达：

> 构建请求可能仍在后台执行，但我暂时无法确认最终状态。当前可追踪的请求 ID 是 `<request_id>`，后续可以基于它继续查状态。

## 有部分表失败时怎么说

MVP 阶段只做结果告知，不做自动重试。

建议表达：

> 这次构建已经跑完，部分表成功、部分表失败。我先把成功结果和失败原因整理给你。失败项自动重试能力还不在这版 MVP 范围内，后续我们可以再补。

## 表清单确认前的边界提醒

- 没有用户确认，不进入构建
- 用户如果只想停在报告阶段，直接结束，不强推系统构建
- 用户如果继续构建，先确认表清单，再调用 API

## 模型边界

- 模型负责对话和中间结构生成
- `build_batch_payload.py` 负责 ID 和请求体生成
- `basebuilder-cli` 负责提交请求、SSE 消费、keepalive 输出和状态补查
- 执行状态以 API 为准，不以对话记忆为准
