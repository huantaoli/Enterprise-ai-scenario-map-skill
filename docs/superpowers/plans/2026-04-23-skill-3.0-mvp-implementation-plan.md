# Enterprise AI Scenario Map Skill 3.0 MVP Implementation Plan

## Objective

Implement the 3.0 MVP on top of the existing skill so that one user request can:

1. generate the existing enterprise AI scenario map report
2. branch into optional system-building planning
3. clarify system intent in 3-4 rounds with early stop
4. produce a confirmed intermediate table list
5. call the batch build API
6. stream progress and show a final summary

This plan follows the approved design in:

- `docs/superpowers/specs/2026-04-23-skill-3.0-mvp-design.md`

## Delivery Strategy

Use incremental implementation in four layers:

1. guidance files
2. deterministic scripts
3. `SKILL.md` orchestration changes
4. end-to-end validation

This order minimizes risk because the user-facing behavior is updated only after the script interface is stable.

## Phase 1: Add Guidance Files

### Goal

Create the reference material the skill will rely on for 3.0 behavior, without changing runtime behavior yet.

### Files

- `references/system-build-clarification.md`
- `references/table-planning-output-schema.md`
- `references/batch-build-api-contract.md`
- `references/mvp-scope-and-fallbacks.md`

### Tasks

1. Write `system-build-clarification.md`
   - define the clarification objective
   - define the 3-4 round cap
   - define early-stop rules
   - define priority dimensions
   - include examples of concise follow-up questions

2. Write `table-planning-output-schema.md`
   - define the allowed output shape
   - define required fields
   - define content quality rules for `user_requirement`
   - include positive examples
   - include invalid examples such as field-level schemas or final API payloads

3. Write `batch-build-api-contract.md`
   - capture request structure
   - capture `batch_accepted`, `job_progress`, `job_complete`, and `batch_complete`
   - capture status endpoint behavior
   - capture stream interruption fallback rules

4. Write `mvp-scope-and-fallbacks.md`
   - define what MVP must not attempt
   - define what the skill should say if build streaming fails
   - define what the skill should say when some items fail
   - define the no-retry MVP posture clearly

### Exit Criteria

- each reference file exists
- each reference file is specific enough to be used by `SKILL.md`
- none of the guidance files contradict the approved design spec

## Phase 2: Implement Deterministic Scripts

### Goal

Build the deterministic execution layer before wiring it into the skill.

### Files

- `scripts/build_batch_payload.py`
- `scripts/runtime_state.py`
- `scripts/stream_batch_build.py`

### Step 2.1: Implement `build_batch_payload.py`

#### Responsibilities

- accept confirmed intermediate table-list input
- generate a stable batch request payload
- generate unique `client_batch_id`
- generate unique `client_item_id` values
- merge default options

#### Suggested CLI Shape

```bash
python scripts/build_batch_payload.py --input <table_list.json> --output <batch_payload.json>
```

Optional flags:

- `--language`
- `--with-generate-flowchart`
- `--prompt-variant`

#### Suggested Internal Functions

- `load_table_list(path)`
- `validate_table_list(items)`
- `generate_batch_id()`
- `generate_item_id(index)`
- `build_payload(items, defaults)`
- `write_payload(payload, output_path)`

#### Validation Rules

- input must be a non-empty list
- each item must contain `table_name` and `user_requirement`
- `user_requirement` must be non-empty
- generated item ids must be unique within the batch

#### Exit Criteria

- script converts a valid intermediate table list into API-ready JSON
- invalid input fails with a clear error message

### Step 2.2: Implement `runtime_state.py`

#### Responsibilities

- save the latest lightweight runtime state to a JSON file
- load the latest saved state
- update `request_id` after `batch_accepted`

#### Suggested Stored Fields

- `client_batch_id`
- `request_id`
- `payload_path`
- `updated_at`

#### Suggested Internal Functions

- `get_state_path()`
- `load_state()`
- `save_state(state)`
- `update_request_id(request_id)`
- `clear_state()`

#### Exit Criteria

- script helpers can persist and reload runtime state reliably
- missing state file is handled gracefully

### Step 2.3: Implement `stream_batch_build.py`

#### Responsibilities

- submit the batch payload to the local API
- consume SSE output
- surface machine-readable progress lines
- capture `request_id`
- fall back to the status endpoint if the stream breaks after acceptance
- return a final summary object

#### Suggested CLI Shape

```bash
python scripts/stream_batch_build.py --payload <batch_payload.json> --api-base-url http://127.0.0.1:1128
```

#### Suggested Internal Functions

- `load_payload(path)`
- `submit_batch(payload, api_base_url)`
- `iter_sse_events(response)`
- `handle_event(event, state_store)`
- `query_batch_status(request_id, api_base_url)`
- `build_final_summary(result)`

#### Output Design

Print stable JSON lines or another stable parseable format for:

- batch accepted
- progress update
- item completion
- final summary
- fallback status lookup result

This should be easy for the skill to relay without complex parsing logic.

#### Edge Cases

- HTTP failure before stream starts
- stream breaks before `batch_accepted`
- stream breaks after `batch_accepted`
- status endpoint returns running state
- status endpoint returns final state

#### Exit Criteria

- script can complete a healthy build stream
- script can recover current status after post-acceptance interruption
- script produces a final summary the skill can render

## Phase 3: Update `SKILL.md`

### Goal

Wire the new 3.0 orchestration into the existing skill without breaking the report-generation baseline.

### Tasks

1. Keep the existing report-generation flow intact.

2. Add a new explicit post-report branch:
   - stop after the report
   - continue into system-building planning

3. Add a clarification stage:
   - cap at 3-4 rounds
   - prioritize missing dimensions only
   - stop early when enough context exists

4. Add a table-planning stage:
   - point to `references/table-planning-output-schema.md`
   - forbid final API payload generation in the model

5. Add a table-confirmation stage:
   - confirm
   - add
   - remove
   - revise

6. Add an execution stage:
   - call `build_batch_payload.py`
   - call `stream_batch_build.py`
   - relay progress updates to the user
   - summarize final outcome

7. Add fallback guidance:
   - use `request_id` status lookup when streaming breaks after acceptance
   - do not attempt failed-item retry in MVP

### Specific Content to Add

- state transition rules
- script invocation examples
- explicit “do not” rules
- user-facing wording guidance for interruption and partial failure

### Exit Criteria

- the skill can describe the full 3.0 path unambiguously
- the old report-only path still works
- the skill does not ask the model to do deterministic script work

## Phase 4: Validation

### Goal

Confirm that the full 3.0 MVP works end to end and that the report-only path remains intact.

### Manual Test Matrix

#### Test 1: Report-Only Path

1. Trigger the skill.
2. Generate the report.
3. Decline system-building planning.

Expected result:

- report is produced
- conversation ends cleanly
- no batch-build scripts are invoked

#### Test 2: Full 3.0 Happy Path

1. Trigger the skill.
2. Generate the report.
3. Accept system-building planning.
4. Complete clarification in 3-4 rounds or fewer.
5. Confirm table list.
6. Build payload.
7. Execute batch build.
8. Observe final summary.

Expected result:

- intermediate table list is valid
- payload is valid
- API call succeeds
- progress is visible
- summary is visible

#### Test 3: Stream Interruption Recovery

1. Start a build.
2. Wait for `batch_accepted`.
3. Interrupt the stream.
4. Query status using saved `request_id`.

Expected result:

- status lookup works
- the user sees a useful current or final status

#### Test 4: Table Confirmation Editing

1. Generate initial table list.
2. Remove one table.
3. Add one table.
4. Revise one table description.
5. Confirm.

Expected result:

- final payload matches the edited confirmed list

### Lightweight Script Checks

- payload generation with valid input
- payload generation failure with invalid input
- runtime state save and reload
- SSE parsing on representative sample events

## Implementation Sequence

Recommended implementation order:

1. create the four new reference files
2. implement `build_batch_payload.py`
3. implement `runtime_state.py`
4. implement `stream_batch_build.py`
5. update `SKILL.md`
6. run manual tests
7. tighten wording and cleanup after validation

## Risks and Mitigations

### Risk 1: `SKILL.md` becomes too heavy

Mitigation:

- keep deterministic logic in scripts
- move formatting rules and schemas into references

### Risk 2: model output drifts from allowed intermediate schema

Mitigation:

- create strict schema guidance with positive and negative examples
- validate input before payload generation

### Risk 3: stream interruption leaves the user without clarity

Mitigation:

- save runtime state as soon as `request_id` is known
- implement status-endpoint fallback before updating `SKILL.md`

### Risk 4: report-only flow regresses

Mitigation:

- keep the new branch strictly after report completion
- validate report-only mode separately

## Definition of Done

This implementation plan is complete when all of the following are true:

1. all four reference files exist and match the design
2. the three scripts exist and work for MVP needs
3. `SKILL.md` supports both report-only and report-plus-build flows
4. a full happy-path run succeeds against the local API
5. streaming interruption can be recovered via `request_id`
6. the user sees a clean final summary without retry support
