# Enterprise AI Scenario Map Skill 3.0 MVP Design

## Goal

Upgrade the existing `enterprise-ai-scenario-map` skill from a report-only flow into a single-entry workflow that:

1. Generates the enterprise AI scenario map report.
2. Asks whether the user wants to continue into system-building planning.
3. Collects enough system context in 3-4 clarification rounds, with early stop when information is sufficient.
4. Produces a confirmed intermediate table-planning structure.
5. Calls the batch build API and streams progress back to the user.

This MVP is intentionally scoped to one successful end-to-end run. It does not include failed-item retry, local SQL persistence, or a history center.

## Product Shape

### Entry Model

Use a single entry skill. The user triggers the skill with a natural-language request about generating an AI scenario map for a company.

The workflow always begins with report generation. After the report is complete, the skill presents an explicit branch:

- stop after the report
- continue into system-building planning

This preserves the richer enterprise context gathered during the report phase and uses it as input for later table planning.

### Why This Shape

- It reuses the strongest part of the current skill instead of replacing it.
- It avoids fragmenting the user mental model across multiple skills.
- It keeps the MVP focused on orchestration, not on redesigning the report workflow.

## Scope

### In Scope

- Reuse the current research, analysis, and report generation flow.
- Add a post-report confirmation step for entering system planning.
- Add 3-4 rounds of system clarification, with early stop when enough information is gathered.
- Generate an intermediate table list in the form `[{ table_name, user_requirement }]`.
- Let the user confirm or adjust the table list.
- Build the batch request payload deterministically in scripts.
- Call `npx basebuilder-cli build --input <payload> --json`.
- Consume CLI JSON Lines progress events and display progress to the user.
- Record `request_id` from the `batch_accepted` event output.
- Query status with `npx basebuilder-cli status <request_id> --json` if the build command breaks after acceptance.

### Out of Scope

- Retrying only failed items.
- Any local SQLite or local task database on the skill side.
- Frontend pages or task center.
- Multi-batch history browsing.
- Complex crash recovery across multiple past sessions.

## Architecture

### Split of Responsibility

The design uses a two-layer split.

#### `SKILL.md`

Responsible for:

- conversation flow
- user-facing explanations
- confirmation gates
- deciding when to stop clarification
- instructing the agent to call deterministic scripts

Not responsible for:

- building final batch JSON
- tracking execution state as a source of truth
- parsing SSE business logic inline

#### `scripts/`

Responsible for:

- deterministic batch payload generation
- SSE request execution
- SSE event parsing
- lightweight runtime-state capture
- status-query fallback when a stream breaks

This keeps non-deterministic reasoning in the skill and deterministic execution in code.

## Dialogue State Machine

### 1. `report_generation`

Reuse the existing skill flow:

- enterprise research
- business analysis
- scenario map generation
- report generation

Output: the existing enterprise AI scenario map report.

### 2. `build_entry_confirmation`

After the report, always ask whether the user wants to continue into system-building planning.

Possible outcomes:

- user declines: end successfully after the report
- user accepts: continue to clarification

### 3. `system_clarification`

Run up to 3-4 rounds. Stop early if enough information is gathered.

Priority dimensions:

1. system goal
2. main user roles
3. core business processes
4. current pain points and constraints
5. whether flowchart generation is needed

Rules:

- ask only for the most missing information each round
- avoid asking all dimensions if earlier context already covers them
- synthesize prior report context into later questions

### 4. `table_planning`

The model generates an intermediate table-planning structure only.

Required output shape:

```json
[
  {
    "table_name": "CRM客户管理",
    "user_requirement": "..."
  }
]
```

Rules:

- no final API payload generation in the model
- no field-level schema generation in the model
- `user_requirement` should include enough business context for the downstream API

### 5. `table_confirmation`

Present the table list and allow the user to:

- confirm as-is
- remove a table
- add a table
- revise a table description

Only after explicit confirmation can execution begin.

### 6. `batch_build_execution`

After confirmation:

1. call a script to build the final batch payload
2. call `npx basebuilder-cli` to submit the batch request and stream SSE events
3. surface `job_progress.message` directly to the user
4. if the command breaks after `request_id` is known, call `npx basebuilder-cli status`
5. summarize success or failure when the batch reaches a terminal state

## File Design

### New Reference Files

#### `references/system-build-clarification.md`

Defines:

- clarification goals
- question priorities
- early-stop conditions
- examples of good follow-up questions

#### `references/table-planning-output-schema.md`

Defines:

- the allowed intermediate output structure
- positive and negative examples
- rules for writing `user_requirement`

#### `references/batch-build-api-contract.md`

Documents the local API contract for the skill:

- request payload shape
- SSE event types
- stream interruption fallback
- status endpoint usage

#### `references/mvp-scope-and-fallbacks.md`

Documents:

- what MVP does not do
- what to tell the user on interruption or item failure
- how to end gracefully without retry support

### New Scripts

#### `scripts/build_batch_payload.py`

Inputs:

- confirmed table list JSON
- optional defaults such as language and flowchart flag

Outputs:

- final batch request JSON

Responsibilities:

- generate unique `client_batch_id`
- generate unique `client_item_id` values
- merge defaults into the batch payload
- keep payload shape deterministic

#### `npx basebuilder-cli`

Inputs:

- batch payload JSON
- API base URL

Responsibilities:

- submit `POST /api/bitable/build/batch`
- parse SSE events
- print progress as stable JSON Lines for the skill to relay
- capture `request_id` from `batch_accepted`
- query batch status if the SSE stream breaks after acceptance
- return a final summary object

## Data Flow

### User to Report

User request -> existing report workflow -> report output

### Report to Planning

Report context + clarification answers -> table planning prompt -> intermediate table list

### Planning to Build

Confirmed table list -> `build_batch_payload.py` -> batch JSON

### Build to Result

Batch JSON -> `npx basebuilder-cli build --input <payload> --json` -> SSE events -> user-facing progress + final summary

### Recovery Path

If SSE breaks:

- use the recorded `request_id`
- call `npx basebuilder-cli status <request_id> --json`
- report the current or final batch state to the user

## Error Handling

### User Declines Build Step

Return successfully after the report. Do not push the user into the system-building phase.

### Clarification Remains Incomplete

After 3-4 rounds, if key information is still missing, proceed using the best available synthesis and explicitly note assumptions in the generated table list.

### SSE Stream Breaks Before `batch_accepted`

Treat as an execution failure and ask the user to retry the whole build step later. There is no request id yet, so no status lookup is possible.

### SSE Stream Breaks After `batch_accepted`

Use the status endpoint with the captured `request_id`. If the status endpoint is reachable, present the current or final status. If it is not reachable, tell the user that the build may still be running and provide the request id.

### Some Items Fail

For MVP:

- show failed items in the final summary
- do not attempt automatic or item-level retry

## Testing Strategy

### Manual Tests

1. Report-only path
   - trigger the skill
   - generate the report
   - decline system build

2. Full build path
   - trigger the skill
   - generate the report
   - accept system build
   - complete clarification
   - confirm tables
   - verify batch build reaches terminal state

3. Stream interruption fallback
   - start a build
   - interrupt SSE after `request_id` is received
   - verify status endpoint recovery

4. Table confirmation edits
   - remove, add, and revise items before confirmation
   - verify payload matches the confirmed set

### Script Validation

- validate payload JSON shape before submission
- validate that generated ids are unique within a batch
- validate that final summaries preserve item-level success or failure

## Implementation Order

1. Update design and guidance files.
2. Add reference files for clarification, output schema, API contract, and MVP scope.
3. Implement `build_batch_payload.py`.
4. Wire execution to `npx basebuilder-cli`.
5. Update `SKILL.md` to wire the new branch and scripts into the existing workflow.
6. Run manual end-to-end validation.

## Open Decisions Resolved

- Use a new git branch for 3.0 MVP work.
- Keep a single skill entry.
- Always start from report generation.
- Add an explicit post-report branch into system building.
- Use 3-4 clarification rounds with early stop.
- Do not add local SQLite in MVP.
- Do not add failed-item retry in MVP.

## Acceptance Criteria

The MVP is successful when:

1. A user can trigger the existing skill and receive the report.
2. The skill asks whether to continue into system-building planning.
3. Clarification ends within 3-4 rounds or earlier when enough context exists.
4. The skill produces a valid intermediate table list.
5. The user can confirm or revise the table list.
6. The scripts can generate a valid batch payload.
7. The batch build API is called successfully.
8. SSE progress can be shown to the user.
9. A final success or failure summary is shown.
10. If the stream breaks after acceptance, the skill can query status by `request_id`.
